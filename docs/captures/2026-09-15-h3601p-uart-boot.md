# Captura UART de boot — ZTE H3601P — 2026-09-15

## Identificação

- **Data:** 2026-09-15
- **Equipamento:** ZTE H3601P
- **Interface observada:** ZTE pad 2 → Raspberry Pi Pico GP2
- **Modo:** captura UART passiva
- **Configuração:** 115200 baud, 8N1
- **Direção:** RX-only no Pico
- **Firmware do Pico:** Passive UART Capture v0.3.0
- **Buffer configurado:** 8192 bytes
- **Bytes capturados no buffer:** 8192
- **Bytes descartados pelo firmware:** 1232
- **Observação:** a captura atingiu o limite do buffer. Portanto, este registro é uma amostra parcial do boot, não uma captura completa.

## Objetivo

Registrar uma evidência reproduzível de que o sinal presente no ZTE pad 2 pode ser decodificado como uma console UART válida utilizando o Raspberry Pi Pico em modo somente leitura.

A captura foi realizada sem transmissão de dados do Pico para o ZTE.

**Importante:** estes valores pertencem à imagem e ao equipamento observados nesta captura. Não devem ser tratados como um mapa universal de flash para todas as revisões do H3601P.

## CRCs observados

O bootloader exibiu, entre outros, os seguintes pares de valores:

```text
crc=0xe7878d22, 0x187872dd
crc=0x198575d7, 0xe67a8a28
crc=0x709215c, 0xf8f6dea3
```

Os valores são registrados aqui como evidência da saída. O projeto ainda não atribui formalmente significado a cada segundo valor apresentado pelo bootloader sem análise adicional do código/formato correspondente.

## Estado da evidência

Esta captura é especialmente relevante porque demonstra que:

1. O sinal em **pad 2** possui temporização compatível com UART.
2. A configuração **115200 8N1** produz texto legível e consistente.
3. O conteúdo é uma sequência real de inicialização do bootloader, e não apenas caracteres isolados.
4. O bootloader expõe informações sobre hardware, NAND, imagens de firmware, kernel e filesystem.
5. O Pico conseguiu obter essas informações sem transmitir dados ao ZTE.

## Limitações desta captura

O firmware v0.3.0 utiliza um buffer de apenas 8192 bytes por canal. Nesta execução:

```text
Bytes: 8192
Dropped: 1232
```

Portanto, pelo menos 1232 bytes foram recebidos depois que o buffer atingiu sua capacidade e não foram preservados pelo firmware.

A captura também termina no meio da tabela de imagens:

```text
+-----+------------+------------+------------+
| Seq |   Kernel   |    Romfs   |   Header   |
+-----+------------+------------+------------+
|  0  | 0x00700000 | 0x...
```

O conteúdo restante da tabela não está disponível nesta aquisição.

## Próxima evolução da captura

Antes de aumentar a capacidade de análise do protocolo, o firmware deve ser alterado para separar claramente:

```text
Pico
  │
  ├── aquisição UART
  │
  └── transporte USB CDC
          │
          ▼
        host
          │
          ├── arquivo bruto
          ├── log interpretado
          ├── metadados
          └── SHA-256
```

O armazenamento deve ocorrer no computador, permitindo capturas arbitrariamente maiores que a RAM disponível no Pico. O Pico deve funcionar como dispositivo de aquisição/streaming, e não como armazenamento permanente da evidência.

## Reprodutibilidade

Para repetir esta experiência:

1. Conectar GND do ZTE ao GND do Pico.
2. Conectar ZTE pad 2 ao GP2.
3. Manter o pad 1 desconectado.
4. Não conectar VCC do ZTE ao Pico.
5. Gravar `firmware/pico/uart_capture/uart_capture.ino` no Pico.
6. Abrir a porta serial USB a 115200 baud.
7. Utilizar o comando `c` para iniciar captura contínua.
8. Reiniciar/ciclar a alimentação do ZTE durante a captura.
9. Encerrar a captura após o boot.
10. Preservar o arquivo bruto antes de qualquer transformação ou análise.

## Observação sobre o formato deste registro

Este documento é um **registro histórico de uma captura experimental**. Os textos e valores acima são transcritos da saída fornecida durante a investigação. Quando uma aquisição bruta estiver disponível diretamente em arquivo, ela deverá ser preservada como fonte primária e este documento deverá funcionar como índice/análise descritiva, sem substituir o arquivo original.
