# ZTE H3601P

## Escopo

O H3601P é o primeiro equipamento-alvo do `zte-pico-tool`. O projeto não assume que todos os H3601P possuem a mesma placa, memória ou firmware.

Variantes fornecidas por operadoras podem alterar interface de gerenciamento, serviços de rede, bootloader e disponibilidade do console serial.

## Investigação inicial

Antes de tentar qualquer dump, registrar:

- modelo exato;
- revisão de hardware;
- etiquetas da carcaça;
- versão de firmware, quando disponível;
- fabricante e modelo do SoC;
- memória RAM;
- fabricante/modelo da flash;
- presença e localização de UART;
- tensão lógica da UART;
- comportamento dos LEDs;
- endereço de gerenciamento observado;
- resultados de captura de boot.

## UART

O primeiro objetivo do projeto é transformar a UART do H3601P em um fluxo capturável no computador.

A configuração inicial sugerida para testes é:

```text
115200 baud
8 data bits
No parity
1 stop bit
```

Essa configuração não é uma garantia para todas as revisões.

### Ligação lógica

```text
ZTE TX → Pico RX
ZTE RX ← Pico TX
ZTE GND ─ Pico GND
```

Não conectar alimentação do ZTE ao Pico.

## Console silencioso

Um UART aparentemente sem saída não prova que os pontos estejam errados. Algumas variantes/bootloaders podem reduzir ou desabilitar mensagens no console original.

Por isso o procedimento deve registrar:

- se há atividade elétrica no TX;
- se a velocidade testada está correta;
- se o GND é comum;
- se RX/TX foram cruzados corretamente;
- se o bootloader efetivamente envia mensagens;
- se a revisão do equipamento corresponde à documentação utilizada.

Um analisador lógico pode ser usado para observar a linha TX sem enviar comandos ao dispositivo.

## SPI-NAND

Algumas informações comunitárias sobre variantes H3601P V9.0.x mencionam SoC ZX279128S, arquitetura ARM Cortex-A9 e memória SPI-NAND Winbond W25N02KV. Essas informações são referências de investigação e não devem ser tratadas como identificação do equipamento sem confirmação física.

A partir da identificação da placa, o projeto deverá criar perfis de hardware, por exemplo:

```text
profiles/
└── h3601p-v9.x.yaml
```

O perfil poderá conter:

- SoC;
- UART;
- baud padrão;
- GPIOs relevantes;
- chip flash;
- tensão de I/O;
- capacidade;
- organização NAND;
- particularidades do bootloader.

## Bootloader

Se a UART oferecer console de bootloader, a investigação deve começar por comandos não destrutivos de identificação e leitura.

O projeto deverá manter uma tabela de comandos por revisão, em vez de assumir uma interface universal:

```text
hardware profile
       │
       ├── bootloader type
       ├── identification commands
       ├── read commands
       └── unsupported commands
```

Nenhum comando de escrita deve ser executado automaticamente.

## Dumps

É importante diferenciar três resultados:

### Captura UART

Arquivo contendo bytes recebidos pela UART durante um período definido.

Isso é uma **captura de console**, não um firmware completo.

### Dump lógico via bootloader

Dados obtidos por comandos de leitura disponibilizados pelo bootloader.

A cobertura depende das capacidades do firmware do equipamento.

### Dump bruto da SPI-NAND

Aquisição direta do conteúdo físico da memória flash.

Pode incluir páginas, OOB, blocos inválidos e estruturas específicas da NAND. A interpretação correta exige conhecimento da organização da memória.

## Evidências

Cada aquisição deve preservar o original:

```text
captures/
└── h3601p-YYYYMMDD-HHMMSS/
    ├── raw.bin
    ├── metadata.json
    ├── sha256.txt
    └── notes.md
```

Nunca editar `raw.bin` para facilitar análise.

## Objetivo de longo prazo

O resultado desejado é uma ferramenta capaz de identificar a revisão, estabelecer uma sessão segura de aquisição e produzir um dump reproduzível quando o hardware e o bootloader permitirem.
